# 逆向与实测记录 / Findings

本文件记录寄存器语义、门控逻辑、以及本项目采用方法的原理与踩过的坑。
所有结论均在 **机械革命 无界15X（WUJIE15XA，BIOS N.1.14MRO50）** 上实测，标"未验证"的即为推断。

---

## 1. 写入通道

设备节点 `\\.\ACPIDriver`（由机械革命控制中心 / OpenRevo 安装的 `UWACPIDriver.sys` 提供，
硬件 ID `ACPI\INOU0000`，供应商名 Uniwill），**免管理员权限**。

```
IOCTL_EC_READ  = 0x9C40A488   输入: u32 addr              输出: u32（低字节为值）
IOCTL_EC_WRITE = 0x9C40A48C   输入: u32 addr, u32 val
```

地址空间：`0x700–0x7FF` 是可写 H2RAM 窗口；`0x800` 以上是主机不可写盲区。
`0x087F`（存储上限）就在盲区里，因此**通过本通道读不到真实值**（恒读 `0xFF`），
要访问它必须走 WMI mailbox `AcpiTest_MULong.GetSetULong`（需管理员）。

## 2. 寄存器表

| 地址 | 语义 | 备注 |
|---|---|---|
| `0x07B9` | **实时上限** bits[6:0]，bit7 = REACHED | 可写。本项目的目标寄存器 |
| `0x087F` | **存储上限**（stored limit） | 盲区，只能经 WMI mailbox；固件用它决定门控是否常开 |
| `0x07C3` | 平台值 / 门控状态（state） | **只读诊断用，不要当配置改**；本机 = `0x07` |
| `0x0770` | ROM ID[0]（`0x0770–0x077D` 为 14 字节 ROM ID 区） | 出厂空槽 `0xFF`；钉扎法会写它 |
| `0x0742` | `SUPPORT_5`；bit2 = 限充门控/控制环路激活 | **唯一可靠的效果判据**，但固件每秒才更新一次 |
| `0x07A6` | `OEM_4`；bits[5:4] = 充电档位（0=长效 1=均衡 2=工作站） | 官方控制台写这里 |
| `0x0740` | PROJECT_ID | WMI mailbox 自检用（本机 `0x1A`） |
| `0x0434/0x0435` | 电池电流 | 与 `Win32_Battery` 的功率/电压换算值一致，可交叉验证 |
| `0x0436/0x0437` | 剩余容量（低/高字节） | |
| `0x0404/0x0405` | 满充容量（低/高字节） | |

## 3. 门控逻辑

```c
bool state_is(uint8_t v) { return xram[0x07C3] == v || xram[0x0770] == v; }

// 固件每秒执行一次
bool limit_enabled = state_is(4) || state_is(5);
if (!limit_enabled) {
    uint8_t stored = xram[0x087F] & 0x7f;
    if (stored == 0 || stored > 100) { disable_control(); return; }
}
enable_control();   // 使用实时上限 xram[0x07B9]
store_limit();      // 实时上限 → 存储区 xram[0x087F]
```

两条互备的启用条件：

1. **门控成立**：`0x07C3` 或 `0x0770` 等于 4/5（产品线授权）
2. **存储值合法**：`0x087F` 落在 1–100

本机 `0x07C3 = 0x07`、`0x0770 = 0xFF`，条件 1 恒不成立；
而 `0x087F` 在盲区里无法直接写 → 这就是"设了不生效"的全部原因。

**关键点**：条件成立期间，固件会执行 `store_limit()`，把实时上限写进存储区。
于是只要**让门控短暂成立几秒**，就能把值"存进固件"，之后靠条件 2 长期维持。

## 4. 本项目方法（存储触发）

```
1. 写 0x07B9 = 目标百分比（如 50 = 0x32）
2. 读出 0x07C3 原值并留存
3. 写 0x07C3 = 0x04，保持 2.5 秒          ← 门控临时成立，固件执行 store_limit()
4. 写回 0x07C3 = 原值（0x07），回读确认    ← 唯一风险点：必须确认恢复成功，失败重试一次
5. 等 7 秒，读 0x0742 bit2 = 1 → 生效
```

- 若 `0x07C3` 本来就等于 4/5（门控原生开），跳过第 3–4 步
- 幂等，可反复执行
- 全程不写 `0x0770`（ROM ID），不碰任何身份字节

### 撤销

```
1. 写 0x07B9 = 0x00
2. 同样走一次 3–4 步 → 存储值归零 → 门控自动回落
```

实测：撤销后 12 秒内电池恢复充电（`Charging=True`，`ChargeRate=34034 mW`）。

## 5. 实测验证矩阵

| 测试 | 结果 |
|---|---|
| 写入后门控置位 | ✅ 7 秒内 `0x0742 bit2 = 1` |
| 从 12% 充到 50% | ✅ 精确停在 50% |
| 重启 | ✅ 保持 |
| 关机 + 拔电源 + 断电 10 分钟 | ✅ 保持（门控仍开，`0x07B9` 仍为 50） |
| 之后再从 48% 充起 | ✅ 停在 50%，`Charging=False` / `ChargeRate=0` |
| 取消限充 | ✅ 12 秒内恢复充电 |
| 平台值保护 | ✅ `0x07C3` 回读 = `0x07`；`0x0770` 始终 `0xFF` |

全程**没有任何软件在运行**（启动项禁用、无计划任务）—— 说明是固件自己在执行。

## 6. 踩过的坑

| 坑 | 现象 | 正解 |
|---|---|---|
| 取消时只关门控 | 界面显示"已取消"，但**电池完全不充电**（插电 30 分钟 `ChargeRate` 恒为 0） | 必须同时清 `0x07B9 = 0`，并触发存储让存储值也归零 |
| 把 `0x0742` bit2 当实时判据 | 一度判断"此位会滞后、不可信" | 该位**每秒才更新一次**，写完等 7 秒再读即可；之前的"滞后"其实是没清 `0x07B9`，控制环路仍在跑 |
| 钉扎 `0x0770` 开门控 | 能生效但值易失，必须常驻 watcher / 开机重放；且改了身份字节 | 改用存储触发，一次写入即持久 |
| 假设"重启/休眠都会复位" | 早期照搬他人文档，未实测 | 实测重启、关机、拔电源都保持；只有**电池彻底耗尽**才丢 |
| 用 `Win32_Battery.EstimatedChargeRemaining` 与任务栏对不上 | 读到 98% / 99% 不一致 | 任务栏口径用 `GetSystemPowerStatus().BatteryLifePercent`；两者可能相差 1% |
| 走 WMI mailbox 需管理员 | `Register-ScheduledTask`/`schtasks` 普通用户均返回 `0x80070005` | 本方法不需要管理员，也不需要用 mailbox |

## 7. 电池健康度：测不到准确值（重要）

本机 BMS **不提供真实老化数据**：

- `powercfg /batteryreport` 里 66 个时间点（2025-06 → 2026-09）满充容量恒为 `80,080 mWh`，
  **精确等于设计容量**，一个 mWh 都没变过
- 循环次数为空，序列号 `00001`，厂商 `OEM` —— 全是占位值

因此**任何工具读到的"健康度 100%"都不可信**。

一个反直觉的点：`RemainingCapacity` 恰好等于 `百分比 × 800.8`，是**派生值**；
所以"用 ΔWh ÷ Δ% 反推容量"这套算法在本机上是**自洽闭环**，永远算出标称值，测不出衰减。

唯一有判别力的做法是**放到自动关机/休眠**时看残余百分比：
若容量真比标称少很多，会在高百分比处突然断电而非干净休眠。实测在 5% 干净休眠 → 未见严重衰减。
